# Take one useful step

You do not need a talk proposal or a large patch to take part. Start with one
question, one exercise, or one small correction.

## Choose the kind of help you need

For a specific role, use [the participation routes below](#choose-a-role).

| Your goal | A useful first step |
| --- | --- |
| Solve a Rust problem | Search the [Rust Users Forum](communities.md#rust-users-forum). If needed, prepare a small example, expected behavior, and exact error. |
| Understand a language proposal | Read the [Rust Internals](communities.md#rust-internals-forum) discussion and linked design notes before adding a question. Proposals can change. |
| Explore types or compilers | Read [Types Team minutes](communities.md#rust-types-team), or inspect a task from the [compiler contribution guide](opportunities.md#find-a-compiler-contribution). |
| Practice with feedback | Try [Exercism Rust](communities.md#exercism-rust). Volunteer mentoring is described; a mentor's availability is not guaranteed. |
| Teach or organize learning | Explore [Rust Edu](communities.md#rust-edu) and [RustBridge](communities.md#rustbridge). Confirm an actual course, chapter, or workshop separately. |
| Find a local group | Use the [regional directory](communities.md#regional-groups). Check its next event, language, access, and joining instructions. |
| Speak or join a working event | Review [calls and activities](opportunities.md). Check the deadline and eligibility on the organizer's page. |

For production agents, types, infrastructure, or robotics, follow the
[four session-to-community paths](../../community/README.md).

## Choose a role

These are routes to investigate. Confirm a current opening, requirements, and
participation rules before offering time or making commitments.

| Role | Preparation and first action |
| --- | --- |
| Attendee or remote learner | Choose a question and use the [learning guide](../../docs/attend-and-learn.md) |
| Speaker | Research earlier talks and draft a [proposal](../speaking/README.md) |
| Workshop teacher | Define one exercise and its [setup requirements](../../templates/workshop-readiness.md) |
| Volunteer | Read an event's published roles; ask its public organizer route about a specific unfilled task |
| Program reviewer | Check the organizer's recruitment route, selection criteria, time needs, and conflicts policy; no reviewer opening is asserted here |
| Mentor | Use a community's stated mentoring process; confirm scope and availability with participants |
| Code or documentation contributor | Follow the project's guide and choose one reproducible issue or unclear page |
| Translator or caption contributor | Confirm permission, terminology, review process, and where the work will be published |
| Local host | Adapt the [small-event example](../organizing/example-event.md) and confirm people and access |
| Sponsor or supporter | Use the organizer's published support route; record terms and keep editorial judgments independent |

**Example contribution:** a learner follows a setup guide and finds an ambiguous
step. They record the source, version, expected behavior, and actual error, then
submit a small correction through the project's process. Until someone reports
that work, this remains an example, not a completed contribution.

## Ask a useful forum question

Rust's [official community guide](https://rust-lang.org/community/) distinguishes
general usage discussion from language/compiler development. Start with the
Users Forum for a usage problem; read existing design discussions before posting
to Internals. Follow each forum's own rules.

Search first. Then include the goal, minimal example, toolchain/library versions,
expected behavior, exact error, and what you tried. Remove credentials and private
data. When solved, explain the result and link the relevant source.

For example: “I expected my worker to finish its current job during shutdown.
Here is a small reproduction and its output. Which cancellation assumption is
wrong?” Fill those fields from an actual run; do not invent the output.

## Make a first contribution

Choose a project you already want to understand. Read its contribution guide,
participation rules, and existing discussions.

1. Find a small task: unclear documentation, a reproducible bug, an example, a
   missing test, a translation, or issue triage permitted by the project.
2. Check that the task is still needed and that nobody is already working on it.
   A help-wanted label is a starting point, not a reservation.
3. Follow the project's process. Describe the problem, the evidence, and the
   smallest useful change. Keep a note of what you learned.

Start with [Tokio](opportunities.md#contribute-to-tokio),
[embedded Rust](opportunities.md#improve-embedded-documentation-or-tooling), or
[Snix](opportunities.md#explore-a-snix-contribution).
Embedded documentation may need no board; hardware tasks have their own setup.
Snix describes early development and unstable APIs.

For this collection, a [source-linked suggestion](../../CONTRIBUTING.md#communities-and-participation)
is enough. You can correct a link or improve a short explanation in your browser.
Preserve the original source, language, and translation credit.

## Learn together

These are formats you can propose, not events hosted by this repository.
Use the [activity template](../../templates/community-activity.md) to state the
scope, preparation, access, and intended result.

| Format | Keep the outcome small |
| --- | --- |
| One talk, one experiment | Read or watch one source, test one claim, and record the result and its limits. |
| Paper or recording club | Prepare two questions, compare interpretations, and keep unresolved questions. |
| Documentation or translation sprint | Improve one page or example; preserve meaning, attribution, and links. |
| Project demo hour | Show one working behavior, one limitation, and one question for feedback. |
| Pairing or first-contribution session | Choose an available task, agree on preparation, and record the actual result. |
| Topic discussion or informal meetup | State the topic and participation rules; publish notes only with consent. |

A proposed activity needs a willing host and confirmed arrangements before it
can be announced. Keep invitations opt-in. Do not publish private chats,
attendee lists, or contact details.

## Check access before committing

Look for the event's own information on cost, remote access, spoken language,
captions, venue access, equipment, and eligibility. Unknown does not mean free,
accessible, unavailable, or closed.

The [opportunities guide](opportunities.md) distinguishes conditional speaker
support from confirmed funding, and past access policies from current offers.
The [Rust Foundation support page](https://rustfoundation.org/project-support/)
describes the Maintainers Fund; this research did not establish an open grant application.

Before starting a new group, read the [Rust community guidance](https://rust-lang.org/community/)
and [RustBridge chapter route](opportunities.md#explore-running-a-rustbridge-workshop).
Use a public participation channel, clear conduct rules, and an achievable scope.
